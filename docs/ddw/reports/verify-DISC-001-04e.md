## Acceptance criteria
- ✅ AC-01 — the repository compares `baseVersion` with the stored `version` under the group lock and raises `GroupRecordConflictError` (`domain/errors.ts`) before writing anything, for an older and for a future version; the 409 `GROUP_RECORD_CONFLICT` is mapped in the HTTP handler (`shared/http`); on the client the sync pass moves a 409 to conflict (`lib/sync/group-sync.ts`) and later passes skip the record; `group-record-conflict-routes.test.ts` "answers 409 GROUP_RECORD_CONFLICT to an older version and writes nothing, not even a log row", "answers 409 to a future version: a client cannot invent one", "answers 409 to an older version and the expense remains", "answers 409 to an older version and keeps the stored settlement" and "keeps one activity row per applied change and none per conflict"; `group-sync-pass.test.ts` "stores a conflict answer, counts it apart from rejections and goes on (AC-01)" and "skips records already rejected or in conflict: a conflict is never retried (FR-01)"; `group-sync-queue.test.ts` "sends a queued edit with the base version of its record and settles it (AC-01)" and "moves a 409 to conflict, keeps the local request and later passes skip it (AC-01)"; `record-version-migration.test.ts` "adds both version columns as integer not null default 1 with their checks (AC-01)".
- ✅ AC-02 — `GroupConflictView` shows both versions side by side with both buttons and highlights the differing fields; the container loads the record and calls `keepMine` or `keepServer`; `markConflict` keeps the local request and the server record, and `keepServer` removes the local change and stores the server copy; `group-conflict-view.test.tsx` "shows both versions side by side with both buttons" and "highlights only the fields that differ, in both columns"; `group-conflict-container.test.tsx` "loads the record and shows both versions with locale-formatted amounts"; `group-queue.test.ts` "a conflict keeps both the local request and the server record (AC-02)" and "keepServer removes the local change and stores the server copy (AC-02)"; `api-client-groups.test.ts` "a 409 GROUP_RECORD_CONFLICT is a conflict outcome carrying the server expense (AC-02)".
- ✅ AC-03 — `keepMine` rebases the record onto the server version and leaves it queued; the next pass resends it with the server version as base, the server applies it as a new version and the overlay shows the record as pending and then synced; `group-queue.test.ts` "keepMine rebases the record onto the server version and leaves it queued (AC-03)"; `group-sync-queue.test.ts` "resends a keepMine change with the server version as base (AC-03)", "writes the server reply to the cache when the edit syncs (AC-03)" and "sends nothing after keepServer: the change is gone (AC-03)"; `group-sync-overlay.test.ts` "shows pending after keepMine: the conflict is cleared and the change is queued again (AC-03)" and "shows pending for a queued edit, and synced once keepServer emptied the queue (AC-03)"; `group-conflict-container.test.tsx` the "keep mine" test that requests a sync pass; `group-record-conflict-routes.test.ts` "applies an edit with the current version and returns version + 1".

## Functional and non-functional requirements
- ✅ FR-01 (a change on an older version is not applied and is marked as conflict): AC-01 above; a stale or future base is refused on the API and the client never retries a conflict automatically; permission rules run first (`group-record-conflict-routes.test.ts` "answers 404 to a non-member and 403 to a member who is not the author, even with a stale version") and two concurrent edits on one version give one 200 and one 409 ("applies two concurrent edits on the same version once: one 200, one 409, final version base + 1").
- ✅ FR-02 (both versions shown, keep one): AC-02 and AC-03 above.
- ✅ FR-03 (the server version stays until the user resolves): AC-04 above; `group-queue.test.ts` "an edit made while the conflict is open keeps the conflict".
- ✅ FR-04 (sync state conflict): AC-05 above.
- ✅ NFR-01 (resolution deletes 0 versions before the user chooses, 1,000 random interruptions): `group-queue.test.ts` "keepServer interrupted at a random step never leaves zero versions" and "keepMine interrupted at a random step never leaves zero versions", each with `RUNS = 1000`; the resolution is one IndexedDB transaction that reads and writes together, so an interruption leaves the state before or after; "a queued record survives closing and reopening the database" and "upgrades a version 2 database in place, keeping its stores and adding an empty group queue" cover the store itself.

## Tests
- ✅ Sad-path tests: every input has an invalid-input test. The API answers 400 to a missing, zero, fractional or non-numeric `baseVersion` on the four routes, 409 to a future one, 404 to a non-member and 403 to a member who is not the author before any conflict; the shared schemas reject the same values and a malformed `current`; the migration rejects version 0; the client treats a malformed 409 body as a generic failure, refuses a path segment that is not a plain id and keeps 404 and 403 apart; the queue refuses an invalid request, an edit of a record queued for deletion, a mark on a record that changed meanwhile, and the resolution of a record with no conflict or not queued; the container renders nothing without a conflict or without a signed-in user.
