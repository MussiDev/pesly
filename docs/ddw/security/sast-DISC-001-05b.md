## Cross-cutting checks

- Authorization on every route: all six new routes run `requireSession` and `requireVerifiedEmail` first (`group-routes.ts:105`) and take the caller's id from the session (`userIdOf(auth)`), never from input. Every use case that touches a group resolves the caller's membership first through `GroupAccess.member` (`record-group-expense.ts:57`, `list-group-expenses.ts:27`, `get-group-expense.ts:21`, `get-expense-options.ts:33`); the default split uses `GroupAccess.admin` (`set-default-split.ts:26`). The one route without a group guard, `GET /groups/personal/shares`, is scoped by the caller's own member rows in the query (`drizzle-group-expense-repository.ts:288`) and is registered before `/groups/:id` so `personal` is never read as a group id (`group-routes.ts:187`).
- IDOR through expense, member, category and account ids: every expense lookup carries the group id of the already-authorized group (`drizzle-group-expense-repository.ts:236`, `:254`); a missing expense and an expense of another group are the same `ResourceNotFound` (`get-group-expense.ts:22-24`); the composite foreign keys `(payer_member_id, group_id)`, `(created_by_member_id, group_id)` and `(member_id, group_id)` make PostgreSQL refuse a cross-group member even if a check were missing (`0027_group_expenses.sql:48-61`); a category of another group fails the in-group lookup and the foreign key mapping (`record-group-expense.ts:74-79`). The payer account is read through the caller's owner scope only (`drizzle-payer-movement-recorder.ts:28-31`, `:44-50`), so another user's account is not found and answers `GROUP_PAYER_ACCOUNT_INVALID`; a `payerAccount` sent for a payer who is not the caller is refused (`record-group-expense.ts:119`). A route test calls every route as a non-member and with an unknown expense id and expects 404 (`group-expense-routes.test.ts:505-544`).
- Atomicity: the expense, its shares, the log row and the payer movement are written in one `db.transaction`, and the recorder builds the movement repository on the open transaction (`drizzle-group-expense-repository.ts:180-226`, `drizzle-payer-movement-recorder.ts:52-83`); tests prove that a failure after the movement insert leaves nothing behind (`drizzle-group-expense-repository.test.ts:196`, `payer-movement-recorder.test.ts:153`).
- Money integrity: amounts are `bigint` end to end (domain `group-expense.ts`, `0027_group_expenses.sql:7`, `:20`, `:35`); allocation uses only `bigint` arithmetic and asserts the sum twice, in the helper (`split-expense.ts:43-47`, called at `:67` and `:104`) and in the use case (`record-group-expense.ts:80-82`); basis points are the only `number`, and they are integers checked by `Number.isInteger` (`split-expense.ts:84`); no `parseFloat`, `toFixed`, `Math.` or float column in the scope (grep) and an introspection test asserts 0 `real`, `double precision` or `numeric` columns (`expenses-schema-introspection.test.ts:84`). The worst case sum of 50 shares at 10^15 is far below the `bigint` column limit.
- Erasure: `payer_movement_id` is `on delete set null` (`0027_group_expenses.sql:55`) and member rows survive as ghosts after account deletion (05a), so the restricting member foreign keys do not block erasure; the user-erasure test was extended for the new tables (`apps/api/test/identity/user-erasure.test.ts`) and a migration test proves the set-null behaviour (`expenses-migration.test.ts:197`).
- Payer movement rules: the movement is created through the same `CreateMovement` use case as `POST /movements`, so account ownership, category kind, rate and date rules are applied again inside the transaction (`drizzle-payer-movement-recorder.ts:62-83`); the date is clamped to the end of today in the payer's time zone rather than refused (`:89-97`).
- Migration 0027: additive (four new tables and one defaulted column), rollback documented with a backup, run order and the journal cleanup (`apps/api/drizzle/rollback/0027_group_expenses.down.sql:1-17`); its journal `when` (1791667061357) is above 0026's 1791661150964 and must still exceed `main`'s maximum at merge (project rule).

## Threat model checklist (R-01 to R-07)

- R-01 cross-group read or write by guessing ids: mitigated by `GroupAccess` first in every use case and group-scoped queries (`drizzle-group-expense-repository.ts:236`, `:254`), same 404 for missing and foreign groups and expenses; tested at `group-expense-routes.test.ts:505-544`, `expense-use-cases.test.ts:500`, `:538` and `drizzle-group-expense-repository.test.ts:283`.
- R-02 a member makes another user's account pay: the account must be the caller's own, open and in the expense currency (`drizzle-payer-movement-recorder.ts:44-50`), and `payerAccount` is refused when the payer is not the caller (`record-group-expense.ts:119`); tested at `expense-use-cases.test.ts:399`, `:423`, `:431` and `payer-movement-recorder.test.ts:63`.
- R-03 shares that do not add up: integer helpers with an asserted sum (`split-expense.ts:43-47`), the sum asserted again in the use case (`record-group-expense.ts:80-82`), 10,000 seeded splits in each of the three modes (`packages/shared/test/split-expense.test.ts:196`, `:208`, `:226`) and 20 concurrent creations (`drizzle-group-expense-repository.test.ts:259`).
- R-04 a partial failure leaves a movement without its expense or the reverse: one transaction on the same handle (`drizzle-group-expense-repository.ts:180`), proven by the forced-failure tests listed above.
- R-05 account erasure fails because movements are referenced: `on delete set null` on `payer_movement_id` (`0027_group_expenses.sql:55`), tested at `expenses-migration.test.ts:197`.
- R-06 sensitive text in logs: audit lines carry ids only (`group-routes.ts:126-135`), tested at `expense-audit.test.ts:25-75`; `description` is not in any log call.
- R-07 a large page or split exhausts the service: `limit` max 100 (`packages/shared/src/groups/expense.ts:13`), split at most 50 members (`:9`), strict bodies, 16 kB body cap (`apps/api/src/app.ts:20`); the cursor is capped at 512 characters (`drizzle-group-expense-repository.ts:70`).
