## Findings by rule

- ✅ F-SAST-01 Hardcoded secrets (CWE-798): the secret-pattern search finds no key, token or connection string in the scope. `.railway/railway.ts` declares `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` as `preserve()` on the worker only and `VAPID_PUBLIC_KEY` on both services; `.env.example` holds empty values. Migration 0039 holds only DDL and one `UPDATE`.
- ✅ F-SAST-02 SQL injection (CWE-89): every `db.execute` template in the scope was read and each interpolated value is a bound parameter. `drizzle-push-delivery-queue.ts`: the instant is bound ISO text cast with `::timestamptz` (`:38-40,47,54-55,94,103-104,116`), `limit ${limit}` and `make_interval(secs => ${LEASE_SECONDS})` are bound numbers (`:49,54`), ids are bound and cast `::uuid` (`:96,105,110`), the status is bound and restricted to `sent | failed | skipped` before use (`:88-90`). `drizzle-push-fan-out.ts`: the id list is built with `sql.join` over one bound `${id}::uuid` per element (`:21-24`), the ids come from the database, and the instants are bound (`:28,34,39`). `drizzle-push-subscription-repository.ts`: `userId` comes from the issued scope and is bound (`:17,40,44,47`), `row.id` is bound (`:38`), the cap is the shared constant `PUSH_MAX_SUBSCRIPTIONS` bound as a parameter (`:49`); the upsert and the remove go through the Drizzle builder. There is no `sql.raw` and no string concatenation that builds SQL in the scope.
- ✅ F-SAST-03 OS command injection (CWE-78): no `child_process`, `exec` or `spawn` in the scope.
- ✅ F-SAST-04 Insecure deserialization (CWE-502): the only `JSON.parse` is the service worker reading a push payload (`push-handlers.ts:46`); its result goes through `pushPayloadSchema.safeParse` and any failure shows the generic notification. The API never parses untrusted JSON itself: bodies go through the strict Zod schemas. The claimed delivery rows are mapped field by field.
- ✅ F-SAST-05 Path traversal (CWE-22): no file access in the scope.
- ✅ F-SAST-06 XSS (CWE-79): the API returns JSON only. In the browser the notification `title` and `body` are passed to `showNotification` as plain text (no HTML interpretation), bounded by `pushPayloadSchema` (title 1 to 40, body at most 300). The settings UI has no `dangerouslySetInnerHTML` or `innerHTML`, and every string comes from the i18n catalogs.
- ✅ F-SAST-07 SSRF (CWE-918): the only outbound request is the push POST. The URL must match `isAllowedPushUrl` (`packages/shared/src/push/push.ts:25-33`): `https://`, one of four allowlisted hosts (`fcm.googleapis.com` and three wildcard suffixes that need at least one label), the host followed directly by `/` (so user-info, ports, IP literals and trailing dots fail), a closed URL-safe character set, one optional query, no fragment, at most 2048 characters. It is checked twice: at subscription (`pushSubscriptionRequestSchema`, `push.ts:41`) and again before every send (`web-push-provider.ts:54`, "tampered row"). The request uses `redirect: 'manual'` (`:91`), so a redirect is never followed and is classified final (`:38-39`), and a 10 s timeout (`:92`). The wildcard regex has a literal dot between labels and the input is capped at 2048, so it is not a ReDoS risk. See I-3 for the residual DNS trust.
- ✅ F-SAST-08 Broken cryptography (CWE-327): `aes128gcm.ts` follows RFC 8291 and RFC 8188 with `node:crypto`. The salt is `randomBytes(16)` (`:36`, a fixed salt only when a test passes one, length-checked at `:37`); the server key pair is a fresh ephemeral `createECDH('prime256v1').generateKeys()` per message (`:39-44`), so the content key and the nonce (both HKDF-derived from the per-message salt and shared secret, `:63-64`) are unique per message and the single-record AES-128-GCM never reuses a key and nonce pair. Key sizes are enforced: user agent point 65 bytes starting `0x04` (`:31`), auth secret 16 bytes (`:34`), content key 16 bytes, nonce 12 bytes, tag 16 bytes, payload size bounded (`:35`); `computeSecret` rejects a point off the curve. VAPID (`vapid.ts`) checks the 65 byte point and the 32 byte scalar (`:19`), signs ES256 with `jose`, audience is the push service origin, expiry is under 12 h (RFC 8292 caps it at 24 h). No `Math.random`, MD5 or SHA-1 anywhere. The worker env check requires the private scalar to derive exactly the configured public key (`env.ts` `derivesPublicKey`). No secret comparison exists in the scope, so there is no timing-sensitive equality.
- ✅ F-SAST-09 Debug mode in production (CWE-489): no `console` call, debug flag or `NODE_ENV` branch in the push code; the env rules make `PUSH_PROVIDER` other than `webpush` a startup error in production (`env.ts` `pushProductionIssues`), so the fake provider cannot run there.
- ✅ F-SAST-10 Logging sensitive data (CWE-532): the routes log `requestId`, `userId` and `subscriptionId` only (`push-routes.ts:79-82,94`), with a comment that the endpoint and the keys never reach the log. The delivery code logs delivery id, notice id, a status code or an error class name (`deliver-due-pushes.ts:183-190,235,240`); `push-job.ts` logs a step name and a class name only, because a network error message can carry the push URL. `web-push-provider.ts` catches and returns an outcome without logging. The logger now redacts `endpoint`, `p256dh`, `authSecret`, `vapidPrivateKey` and `VAPID_PRIVATE_KEY` at three depths, and `body.keys.auth` and `keys.auth` paths (`logger.ts`), and its error serializer never copies Drizzle query params (`logger.ts:83-85,112`), so a failed upsert does not leak the endpoint or keys through `err.message`. The unsubscribe is a `POST` with a body so the endpoint stays out of access logs (`push-routes.ts:88`). The push text carries no amount or account name (`push-payload.ts`: a statement notice is re-rendered from the due day alone, and a budget alert is never pushed).
- ✅ F-SAST-11 Unrestricted upload (CWE-434): no upload surface.
- ✅ F-SAST-12 Missing CSRF protection (CWE-352): the two state-changing routes are `PUT` and `POST` behind `requireSession` and `requireVerifiedEmail` (`push-routes.ts:57`), under the existing cookie and origin protection of the API; `GET /push/config` is read-only and returns only the public VAPID key.
- ✅ F-SAST-13 Critical/High CVE in a dependency: no `package.json` or `pnpm-lock.yaml` change; the audit is re-run by the release gate.
- ✅ F-SAST-14 Incomplete input validation (CWE-20): both bodies go through `validate({ body, response })`. `pushSubscriptionRequestSchema` checks the endpoint allowlist, `p256dh` as exactly 87 base64url characters whose last character leaves zero padding bits (the 16 allowed characters were checked against the bit layout: 520 bits in 522), `auth` as 22 characters with the last one in `AAQgw` set (128 bits in 132); the use case then proves the point is on the curve (`manage-push-subscriptions.ts:427`, `p256-point.ts`). The database repeats the lengths as check constraints (migration 0039). Env: VAPID keys are checked for length, alphabet and the leading `0x04`; the subject must be one line and a `mailto:` or `https:` value; the job interval is an integer from 1 to 60.
- ✅ F-SAST-15 Insecure error handling (CWE-209): an invalid curve point is a `VALIDATION_FAILED` `AppError` naming only `body.keys.p256dh`; an unknown unsubscribe is a 404 through `notFoundUnlessAllowed`; the central error middleware sends only a code. Every `catch` in the scope either maps to a typed outcome with a comment (`web-push-provider.ts:74,95`, `p256-point.ts:12`, `env.ts` `derivesPublicKey`) or logs a class name and keeps the row under its lease (`deliver-due-pushes.ts:181-190`).
- ✅ F-SAST-16 Medium CVE in a dependency: none (no dependency changed).
- ✅ F-SAST-17 Unsafe function (CWE-95): no `eval`, `new Function` or string timers in the scope.
- ✅ F-SAST-18 Suppressions complete: no suppressions in this report; the scope has no `eslint-disable`, `@ts-ignore` or `@ts-expect-error`, and no `any`.
- ✅ F-SAST-19 Suppressions within review window: no suppressions in this report.

## Cross-cutting checks

- Open redirect in `notificationclick`: the target is never taken from the push as is. `resolveTarget` (`push-handlers.ts:55-66`) accepts only a string that starts with `/`, not `//`, with no backslash, resolves it against the worker origin and requires the resolved origin to equal that origin, otherwise it returns `/`; a tab or newline smuggled to build `//host` is stripped by the URL parser and then fails the origin check. The payload schema independently requires `^/(?!/)[^\\]*$` (`push.ts:69`), and the server always builds the link itself as `/<language>/notices` (`pushNoticesLink`). Only an own-origin window is focused or navigated (`isOwnWindow`, `:73-79`).
- Cross-user delivery: a delivery is sent only when the subscription owner equals the notice owner, otherwise it is skipped (`deliver-due-pushes.ts:196-203`); a subscription that moves to another user deletes the pending deliveries of the previous owner's notices in the same transaction (`drizzle-push-subscription-repository.ts:33-40`). The fan-out joins `push_subscriptions.user_id = notices.owner_id`, so a notice is fanned out only to its owner's devices.
- Owner scoping and 404 semantics: `remove` filters by `scopedTo(scope, { owner })` and by endpoint, so another user's subscription answers 404, never 403; the use case receives an issued scope from the policy (`DenyAllGroupMembershipReader`: push is personal, no group access).
- Concurrency and abuse: the subscription store takes a per-user advisory lock and keeps the 10 most recent rows, so the cap cannot be raced; claims use `for update skip locked` with a 120 s lease and at most 5 attempts (also a database check), so two workers never send the same delivery and a stuck row ends as `failed`; sends go through a process-wide concurrency limiter; the job interval is capped at 60 s.
- Secret isolation: `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` and `PUSH_JOB_INTERVAL_SECONDS` are fields of the worker schema only (`env.ts` `workerOnlyFields`); the API schema is built from the common fields, so stray values are ignored. `push/index.ts` exports only the subscription side and `jobs.ts` is deliberately not re-exported, so the API process never imports the delivery queue or the provider.
- Migration 0039: additive (two new tables, one new nullable column, indexes). The only data statement is `UPDATE "notices" SET "push_handled_at" = now()`, a constant with no input, so notices from before the deploy are never pushed; it runs before the partial index on unhandled notices is built. Foreign keys cascade on delete from users and notices, so no orphan delivery stays after an account deletion. No drop, rename or data loss; the rollback file exists under `apps/api/drizzle/rollback`.
- Service worker: the cache keeps only same-origin pages and the API origin is never stored (`sw.ts:240-242,291`); the `message` handler validates its input before use; push registration uses `userVisibleOnly: true` and the permission is requested only from the user's action in `push-client.ts`.
- Money and time: no amount is handled in the scope; the due day in a statement text is formatted with a fixed `UTC` zone from a validated `YYYY-MM-DD`.

## Threat model checklist (threat-DISC-001-08d)

- Server-side request forgery through a crafted endpoint: allowlist at subscribe and at send, no redirects, timeout (F-SAST-07). Mitigated.
- Decryption or forgery of a push by a third party: per-message ephemeral key and random salt, validated key sizes, VAPID signed with a key that must match the published public key (F-SAST-08). Mitigated.
- Another user's notice text reaching a device: owner check at send, pending deliveries purged on an owner change, fan-out joined by owner. Mitigated.
- Leak of the endpoint, keys or the VAPID private key through logs or errors: redaction, error serializer, ids and class names only, private key held by the worker only (F-SAST-10). Mitigated.
- Open redirect or script injection through a notification: server-built link plus own-origin resolution, plain-text rendering (F-SAST-06 and the open redirect check). Mitigated.
- Delivery storm or double send: lease, skip locked, 5 attempts, backoff capped at 900 s, notices older than 24 h are not fanned out, the limiter and the per-user subscription cap. Mitigated.
- Fake provider running in production: production env rules reject it at startup. Mitigated.
