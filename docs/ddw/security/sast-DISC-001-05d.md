## Cross-cutting checks

- Authorization order: every change use case runs group access first (`GroupAccess.member`, `update-group-expense.ts:49`, `delete-group-expense.ts:31`, `update-settlement.ts:46`, `delete-settlement.ts:31`), then loads the record scoped by group id (`getExpense` and `getSettlement` filter on both ids, `drizzle-group-expense-repository.ts:391-396`, `drizzle-group-settlement-repository.ts:190-201`), then the permission rule (`assertCanChangeRecord`, `group-change.ts:41`: author or admin, 403 otherwise), then the consolidated rule, then the former-member rule, then the new values. A non-member, a user who left (the `left_at is null` filter on every membership lookup) and a missing group all answer 404 before any record is read; a member who is not the author or an admin gets 403 only after the record is proven to belong to the group, so a record id of another group answers 404 and never 403. The caller comes from the session (`userIdOf(auth)`), never from input. The activity list needs only active membership (`list-activity.ts:24`).
- IDOR through record and member ids: expense and settlement ids are always paired with the authorized group id in the read and again in the locked read (`drizzle-group-expense-repository.ts:342-347`, `drizzle-group-settlement-repository.ts:240-248`, `:356-360`), so a record id from another group matches nothing; share members are locked with `groupMembers.groupId = groupId` and a count mismatch aborts (`drizzle-group-expense-repository.ts:358-364`), and the composite foreign keys `(member_id, group_id)` on shares, settlements and the log make PostgreSQL refuse a cross-group member even if a check were missing. The activity list filters on the group id (`drizzle-activity-log-reader.ts:41`) and the cursor only positions that query. The 405 handler checks membership first and ignores the entry id, so it is no oracle for log entries (`group-routes.ts:605-609`).
- Immutability trigger (migration 0030): a row-level `BEFORE UPDATE OR DELETE` trigger raises `restrict_violation` for every update and for every delete except when the group row is already gone (`0030_group_activity_log_changes.sql:7-16`). The carve-out cannot be used to delete log rows while the group exists: a direct `DELETE` on the log runs with the group row visible, so the `NOT EXISTS` is false and the delete is refused (tested at `activity-log-every-write-path.test.ts:446` for a row, a group, and a no-op on a missing group); the cascade from `DELETE FROM groups` runs its referential action after the group row is deleted, so only that path passes (tested at `activity-log-migration.test.ts:211`). The application has no group deletion path (no `delete(groups)` in the source). Changing `group_id` is an `UPDATE` and is refused, so a row cannot be moved to a group that is about to be deleted. Bypasses that remain are all privileged database operations and are listed as I-2: `TRUNCATE` (row triggers do not fire), `ALTER TABLE ... DISABLE TRIGGER` or `DROP TRIGGER` (table owner), `session_replication_role = replica` (superuser) and a search-path substitution for the unqualified `groups` name; none is reachable from the API, whose statements are all bound Drizzle builders.
- Lock ordering and deadlocks: every write path takes the group row first, then the record, then member rows in id order. Expense change: group `for share`, expense `for update`, members `for share` ordered by id (`drizzle-group-expense-repository.ts:342-362`), the order creation uses; settlement change: group `for update`, then the settlement read and the members `for share` ordered by id (`drizzle-group-settlement-repository.ts:240-248`, `group-locks.ts:37-44`); removal: group `for update`, then the member row (05c). No path takes a member row and then waits on the group row, so there is no cycle among the group-module locks; two edits of one expense queue on the expense row and the second reads what the first left (tested at `drizzle-expense-changes.test.ts:498`). The one cycle found crossed into the movements module (L-2, fixed in f0b122b by locking the movement before the expense row).
- Atomicity: the record change, the shares or legs, the log row and the payer movement rewrite or removal are written in one `db.transaction` (`drizzle-group-expense-repository.ts:209-286`, `:288-330`, `drizzle-group-settlement-repository.ts:341-390`, `:392-420`); the log `before` is rebuilt from the row read under lock, never taken from the caller (`drizzle-group-expense-repository.ts:253-262`, `drizzle-group-settlement-repository.ts:376-385`); tests prove that a failure after the log insert and a failure of the movement rewrite leave the record, the log and the movement unchanged (`drizzle-expense-changes.test.ts:400`, `:418`, `drizzle-settlement-changes.test.ts:250`, `:363`, `activity-log-every-write-path.test.ts:408`).
- Snapshot content: every amount of a snapshot is `bigint.toString()` and every date an ISO string, shares sorted by member id and legs by currency (`group-change.ts:119-146`), and the shared schema accepts only an integer string for an amount (`minorUnitsStringSchema`, `activity.ts:33`), so a jsonb number, which PostgreSQL stores as an exact numeric but JavaScript would round past 2^53, is never produced; the columns are `jsonb` with no money column (tested at `activity-log-introspection.test.ts:35`, `:40`) and the log table has no float column.
- Information disclosure: the log is readable by active members only and carries ids, amounts, descriptions and shares of that group by decision (spec D9: members already see this data); it returns no email and no user id (`group-activity-presenter.ts:14-24`, `activity.ts:62-71`), only member ids, and the group id is left out of the response. Error bodies carry a code only. A former member is outside every lookup.
- DoS bounds: `limit` max 100, cursor at most 512 characters, body at most 16 kB (`apps/api/src/app.ts:20`), at most 50 split members per expense, one transaction per change holding the group lock for a short, bounded number of statements (about 10 for an expense change), keyset pagination over the index `(group_id, created_at desc, id desc)` (`schema.ts:356-360`); the log grows by one row per change and is never read in full.
- Mass assignment: every body and the query are `z.strictObject`; currency, payer and creator come from the stored row (`update-group-expense.ts:80`, `:91`, `:96`), the settlement patch can change only `amount` and `occurredAt` and the repository `set` names only those two columns (`drizzle-group-settlement-repository.ts:356`), the expense `set` names amount, date, category, description and split mode only (`drizzle-group-expense-repository.ts:229-236`); a consolidated settlement is refused twice, in the use case and again under lock (`update-settlement.ts:50`, `drizzle-group-settlement-repository.ts:345`), so legs and rate cannot be forged.
- Payer movement rewrite under the payer's scope: the movement id is read from the stored expense row, never from the request, and the write scope is the stored payer's own owner scope with the deny-all group reader (`drizzle-payer-movement-recorder.ts:122-126`); the movement is read through that scope first (`:183`) and a movement of another user answers not found and is left alone (tested at `payer-movement-recorder.test.ts:276`, `:315`); the account, category, tags and rate are kept from the stored movement, so an editor cannot repoint the movement to another account, and only amount, date and note move (`:196-205`). An admin editing another member's expense therefore changes that member's personal movement, which is by design (I-3).
- Erasure and retention: member rows survive as ghosts after account deletion (05a), so the restricting member foreign key of the log does not block erasure; `payer_movement_id` is `on delete set null` (`schema.ts:223-225`), so erasing the payer's account does not fail on the movement. The immutable log keeps free-text descriptions after erasure (I-4).
- Migration 0030: additive for data (two nullable columns, one check replaced, one added, one function and one trigger); the rollback is documented with a backup, run order and idempotent guards (`0030_group_activity_log_changes.down.sql:1-28`) and deletes the change rows it cannot keep, which the header states; its journal `when` is above 0028's and must still exceed `main`'s maximum at merge (project rule).

## Threat model checklist (R-01 to R-09)

- R-01 a non-member or a user who left reads the log or changes records by guessing ids: mitigated by `GroupAccess` first in every use case, the `left_at is null` filter on every membership lookup, group-scoped record and log queries and a same-404 policy for missing, foreign and left groups (`update-group-expense.ts:49-51`, `list-activity.ts:24`, `drizzle-activity-log-reader.ts:41`); tested at `group-change-routes.test.ts:449`, `:469`, `:488`, `change-use-cases.test.ts:298`, `:317`, `:328` and `activity-log-reader.test.ts:104`.
- R-02 a member changes or deletes a record of someone else: the permission rule runs after group access and before any value is read or written, 403 for a member who is neither the author nor an admin (`group-change.ts:37-42`, `update-group-expense.ts:52`, `update-settlement.ts:49`); tested at `group-change-routes.test.ts:88`, `:210`, `change-use-cases.test.ts:249`, `:266`, `:284`.
- R-03 a change is made without a log entry, or the log is rewritten: the log row is inserted in the same transaction as the change in all four repository paths, the trigger refuses update and delete, and the three 405 routes answer after the membership check (`drizzle-group-expense-repository.ts:253`, `:305`, `drizzle-group-settlement-repository.ts:376`, `:409`, `0030_group_activity_log_changes.sql:7-16`, `group-routes.ts:605-609`); tested by a test over every write path at `activity-log-every-write-path.test.ts:373`, `:408`, `:446`, the trigger at `activity-log-migration.test.ts:181`, `:199`, `:211` and the 405 at `group-change-routes.test.ts:418`.
- R-04 an edit breaks the zero-sum balances: balances are derived on read from rows, the shares of an edit are allocated by the creation helper and asserted to add up (`allocate-expense-shares.ts`), and a settlement edit replaces its single leg together with the amount in one transaction; tested with 10,000 random creates, edits, deletes and settlements against an independent ledger at `balances-random-edits.test.ts:63` and `change-use-cases.test.ts:915`, and at `group-change-routes.test.ts:103`, `:228`. - R-07 concurrent edits corrupt the shares: group lock plus the expense row `for update`, `before` rebuilt under lock, the second edit reads the first's result (`drizzle-group-expense-repository.ts:342-347`); tested at `drizzle-expense-changes.test.ts:498`. L-1 documented the one lost update on the settlement patch, fixed in f0b122b.
- R-08 sensitive text reaches the application logs: audit lines carry ids only, the database error serializer drops bound parameters, and the error logger never logs the body (`group-routes.ts:184-192`, `logger.ts:63-100`, `error-handler.ts:140-142`); tested at `change-audit.test.ts:23`, `:71`.
- R-09 the payer movement drifts from the expense: rewritten or deleted in the same transaction under the payer's scope (`drizzle-group-expense-repository.ts:263-270`, `:315-319`, `drizzle-payer-movement-recorder.ts:179-215`); tested at `drizzle-expense-changes.test.ts:332`, `:356`, `:418`, `:523`, `change-use-cases.test.ts:491`, `:565`, `payer-movement-recorder.test.ts:215`, `:296`.
