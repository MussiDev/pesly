## Cross-cutting checks

- Authorization order and disclosure: in every changed use case the order is group access (`GroupAccess.member`), the record read scoped by group id (`getExpense` and `getSettlement` filter on both ids), the permission rule, the new-value validation, and only then the repository, where the lock is taken, the acting member is re-read (404 when left) and the version is compared. The conflict body therefore reaches only an active member who may change that very record (R-02). No value check or former-member check that runs before the repository reveals a record: they answer the same codes as before 04e.
- Lost updates and TOCTOU on the version: the read of `stored.version` and the write happen in one `db.transaction` under the group lock (`for share` plus the expense row `for update` for an expense, `for update` on the group for a settlement), and the increment is `version + 1` computed by the database on the locked row, not from a value read earlier (`drizzle-group-expense-repository.ts:242`, `drizzle-group-settlement-repository.ts:376`); two writers with the same `baseVersion` therefore serialize on the lock and the second reads the first's version and gets a conflict (tests `drizzle-expense-changes.test.ts`, `drizzle-settlement-changes.test.ts`, `group-record-conflict-routes.test.ts`). The pre-lock read in the use case feeds only the permission rule (author and group role), which 04e does not change; it never feeds a value that is written, which keeps the 05d fix for the stale settlement patch intact (`update-settlement.ts:75-80`). Every writer of `group_expenses` and `group_settlements` is the create path (version defaults to 1) or the two update paths that bump the counter; the `on delete set null` of `payer_movement_id` changes no content field and not the version, so it cannot hide a conflict.
- Lock ordering: 04e adds no lock and does not change the order (group, then payer movement, then expense row, then members in id order for an expense; group `for update` first for a settlement); the version comparison is a read of the row already locked and it throws before any write, so a conflict rolls the transaction back with nothing written, including the log row and the payer movement (R-01).
- Atomicity and logging: a conflict writes nothing, so no activity log row exists without a change; an accepted change still writes its log row in the same transaction (05d) and bumps the counter in the same statement as the new values.
- Migration 0031 and rollback: `ADD COLUMN ... integer DEFAULT 1 NOT NULL` with a constant default is a metadata-only change on PostgreSQL 11 and later (no rewrite, R-08); the two `ADD CONSTRAINT ... CHECK` statements validate the existing rows with a scan under a brief `ACCESS EXCLUSIVE` lock (I-3); no data is lost; the rollback is guarded (`IF EXISTS`), documented with a backup, run order (before the rollback of 0030) and journal cleanup, and the `created_at` it deletes (`1791760000000`) equals the journal `when` of idx 31 (`apps/api/drizzle/meta/_journal.json`), which is above the maximum on `origin/main` (`1791750000000`) and must still exceed `main`'s maximum at merge (project rule).
- Forged 409 and the client (R-05): the client treats a 409 as a conflict only when the code is `GROUP_RECORD_CONFLICT` and `details` parses as `groupRecordConflictSchema`; a conflict code with a malformed or missing `details` becomes `INTERNAL` and the change is neither dropped nor flagged as a conflict (`apps/web/src/lib/api-client.ts:630-637`); any other 409 goes through the generic error schema. A well-formed forged body can only come from a party that already controls the API response, which the HTTPS origin rules out; even then the stored record must carry the same id, group id and kind as the queued change, or `checked` throws and nothing is stored (`apps/web/src/lib/local-store/group-queue.ts:76-85`, `:405-421`); the local change is kept untouched in every case.
- Resolution atomicity (R-04): `keepMine` and `keepServer` run in one IndexedDB transaction over `groupQueue` and `reference` (`group-queue.ts:429-474`); a throw or an abort inside the request callbacks aborts the whole transaction (`transact`, `:145-183`), the record is re-read inside the transaction and refused when it is no longer queued or has no conflict (`:451-453`), and `keepServer` deletes the queue record and writes the server copy to the cache in the same transaction (`:505-510`); `markGroupConflict`, `settleGroupSent` and `markGroupRejected` are guarded by the `revision` read inside their own transaction, so a change edited while it was in flight is not settled or flagged by an older answer (`:405-421`, `:517-553`). The one write that is not in the resolution transaction is the cache update after a sent change (`apps/web/src/lib/sync/group-sync.ts:90`): the queue is settled first and the copy is replaced on the next online load, so no version is lost.
- Sync pass and conflicts (R-06): a record with a `conflict` or a `rejection` is filtered out of every later pass (`apps/web/src/lib/sync/sync-pass.ts:181`), a conflict answer does not stop the pass and is not counted as a rejection, and network and server failures keep the 04c stop-and-backoff path; the group queue runs only when the movement pass did not stop, under the same lock (`apps/web/src/lib/sync/sync-queue.ts:127-144`).
- Wipe on sign out (04d): `wipeLocalData` deletes the whole IndexedDB database of the user with `indexedDB.deleteDatabase`, after writing the marker and clearing the session pointer (`apps/web/src/lib/local-store/wipe.ts:41-52`), and `resumePendingWipes` finishes an interrupted one; it lists no store, so the new `groupQueue` store (`apps/web/src/lib/local-store/database.ts:28-32`, created in the version 3 upgrade) and the `groupRecord:<kind>:<id>` keys of the `reference` store go with the database, and the wipe is invoked on sign out and account deletion (`apps/web/src/features/shell/use-sign-out.ts:33`, `apps/web/src/features/profile/containers/delete-user-container.tsx:141`). The `DATABASE_VERSION` bump to 3 keeps the data of versions 1 and 2 and does not block on another tab (`database.ts:95-99`). No finding.
- Information disclosure on the device: the server copy in conflict and the `keepServer` copy live only in the user's own IndexedDB database and nowhere else (no `localStorage`, no cookie, no log); both are removed with the database on sign out.
- DoS bounds: the version check is one integer comparison inside a transaction that already existed; body limits (16 kB) and query bounds apply; the conflict body is one record, bounded by the 50-member split cap; a stuck conflict is skipped by passes so it cannot loop requests.

## Threat model checklist (R-01 to R-08)

- R-01 a stale change overwrites another member's work: mitigated by the required `baseVersion`, its comparison under the lock before any write and a 409 with nothing written (`drizzle-group-expense-repository.ts:394`, `drizzle-group-settlement-repository.ts:255`); tested at `group-record-conflict-routes.test.ts`, `drizzle-expense-changes.test.ts` and `drizzle-settlement-changes.test.ts`.
- R-02 a conflict reveals a record to someone without access: group access, the permission rule and the acting-member check all run before the comparison (`update-group-expense.ts:46-52`, `drizzle-group-expense-repository.ts:389-397`); a non-member and a user who left get 404, a member without edit rights gets 403, never a conflict body.
- R-03 a client forces a write with a future or missing version: a missing, zero, negative or fractional value is a 400 (`packages/shared/src/groups/expense.ts:19-30`), a higher value than stored is a conflict because the test is inequality.
- R-04 the user loses a version before choosing: one IndexedDB transaction per resolution (`group-queue.ts:429-474`), tested with interruptions at every step in `apps/web/test/group-queue.test.ts`.
- R-05 a forged 409 body makes the client drop a local change: the body must parse as `groupRecordConflictSchema`, else it is `INTERNAL` and the change stays queued (`api-client.ts:630-637`); the stored server record must match the queued record's id, group and kind (`group-queue.ts:76-85`). A malformed 409 never discards the local change.
- R-06 a conflict is retried in a loop: conflicted records are filtered out of every pass (`sync-pass.ts:181`); tested at `apps/web/test/group-sync-pass.test.ts`. The one loop that remains needs a server that answers a record of another kind or id (I-2).
- R-07 sensitive text reaches the logs: the conflict line and the audit lines carry ids and versions only, the error handler never logs `details` (`group-routes.ts:213-226`, `error-handler.ts:161-163`); tested at `group-record-conflict-routes.test.ts`.
- R-08 the migration blocks writes on a large table: the column is a constant default (metadata only); the two checks scan the table once, see I-3; rollback documented and tested at `apps/api/test/groups/record-version-migration.test.ts`.
