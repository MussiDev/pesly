## Cross-cutting checks

- Ownership and IDOR: the owner id always comes from the session scope (`budget-routes.ts:60-69`, `scope.userId`), never from input. Every budget query carries `scopedTo(scope, { owner: budgets.ownerId })` (`drizzle-budget-repository.ts:34-36`: read, list, update lock, update and delete); a foreign or unknown budget id yields `null` or `false` and the use cases answer `ResourceNotFound` (404), never 403 (`update-budget.ts:25`, `:42`). The version join also matches `owner_id` on both sides (`:66-69`). Composite keys `(budget_id, owner_id)`, `(version_id, owner_id)` and `(category_id, owner_id, kind)` make PostgreSQL refuse a child pointing at another owner's row even if application code had a gap (`0034_budgets.sql:42-55`).
- Foreign categories: `assertBudgetCategories` reads the ids through a reader scoped by owner (`drizzle-category-reader.ts:16-18`); any id not found (unknown or another user's) throws the same 404 (`dependencies.ts:35`); an income category is 400 `BUDGET_CATEGORY_KIND_INVALID`, an archived one 409 `CategoryArchived`. Backstop: the deferred composite key; its violation maps to 404 (`drizzle-budget-repository.ts:28-32`), so a category deleted between the check and the insert answers like a missing id. The subcategory expansion reads children through `scopedTo(scope, { owner: categories.ownerId })` (`:104-110`).
- Mass assignment: no body field reaches a column that is not meant to be edited; `ownerId`, `id`, `createdAt` and `effectiveFrom` are set by the server (`create-budget.ts:19-25`, `mergeVersion` in `domain/budget.ts:57-69`), and currency is not accepted on update (strict object).
- Money: the search for `parseFloat`, `toFixed`, `Number(` and float, real, double or numeric column types returns no hit in the scope; the amount is `bigint` in TypeScript (`BigInt(input.amount)`) and `bigint` in PostgreSQL (`0034_budgets.sql:29`), serialized as an exact integer string (`budgetResponseSchema.amount`); thresholds are `smallint` integers. `Number.isInteger` in `thresholds.ts` validates an integer percentage and is not money arithmetic. A test asserts the schema has no real, double or numeric column (`apps/api/test/budgets/schema-introspection.test.ts:63`).
- Concurrency and the 50-budget limit: creates take a transaction-scoped advisory lock keyed on the owner, then count, so two requests at 49 cannot both pass (`drizzle-budget-repository.ts:153-160`); the lock key is per user, so one user cannot block another. An update locks the budget row `for update` before replacing the month's version (`:187-193`), so the unique `(budget_id, effective_from)` cannot race with itself.
- Audit logging: created, changed and deleted lines carry request id, user id and budget id only (`budget-routes.ts:73-79`, calls at `:95`, `:127`, `:143`); the delete line is emitted only after the use case succeeded (a missing budget throws first).
- DoS bounds: 50 budgets per user (enforced under the lock, `drizzle-budget-repository.ts:19`, `:158`), 50 categories and 5 thresholds per request (`budget.ts:8-10`, `:23-31`), the 16 kB body cap already in the app; the category `inArray` lists at most 50 bound ids; reads are set-based (versions, selections, thresholds, children), not per budget, bounded by 50 budgets. Version rows grow by at most one per budget and month (unique key).
- Migration 0034: additive, four new tables, no change to existing data. The category key is edited by hand to `DEFERRABLE INITIALLY DEFERRED` (`0034_budgets.sql:40-41`, documented in the file and in `schema.ts:91-98`); it stays `ON DELETE no action`, so deleting a category a budget uses still fails at commit, while the cascade from `users` (which deletes categories and budgets in separate internal statements) succeeds because the check runs at the end of the whole delete. drizzle-kit cannot model this, so a future `drizzle-kit generate` that diffs the key could emit an immediate version; the introspection test that expects exactly one deferred budget key (`apps/api/test/budgets/schema-introspection.test.ts:138`) is the guard. Rollback `0034_budgets.down.sql` drops the four tables child first, is idempotent, states the backup and run order, and removes the journal row by `created_at = 1791770000000` guarded by `to_regclass`; it loses all budget data by design and touches nothing else (categories and users stay). The journal `when` (1791770000000) exceeds main's maximum (1791760600000); index 33 is skipped (reserved numbers, project rule).
- Erasure and cascade: `budgets.owner_id` cascades from `users`, and versions, selections and thresholds cascade from the budget, so account erasure removes every budget with no extra erasure step; the deferred category key is what lets the user's categories go in the same cascade. The erasure test covers the three child tables and the same-statement key (`apps/api/test/identity/user-erasure.test.ts:99-102`, `:619-633`). No budget data is shared with another user, so nothing needs anonymizing.
