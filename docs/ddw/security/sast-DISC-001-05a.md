## Cross-cutting checks

- Authorization on every route: all 13 routes run `requireSession` and `requireVerifiedEmail` first (`group-routes.ts:105`) and take the caller's id from the session (`group-routes.ts:66-69`), never from input. Every use case that touches a group resolves the caller's membership first through `GroupAccess.member` (`apps/api/src/groups/application/group-access.ts:13-17`); an admin-only action uses `GroupAccess.admin` (`:19-23`): `update-group.ts:20`, `make-admin.ts:20`, `create-group-category.ts:24`, `update-group-category.ts:31`. The only routes without a membership guard are `/groups/join` and `/groups/claim`, where the token is the credential by design (`join-group.ts:16-19`, `claim-ghost-member.ts:16-19`); `POST /groups` and `GET /groups` need none (the list is filtered by the caller's own `user_id`, `drizzle-group-repository.ts:181`).
- IDOR through member and category ids: every lookup by member id carries the group id of the already-authorized group (`drizzle-group-repository.ts:98`, `:147`, `:262`, `:310`); categories update with `group_id` and `id` in the same `where` (`:364`) after an in-group existence check (`update-group-category.ts:32-33`); the composite foreign keys `(member_id, group_id)` and `(created_by_member_id, group_id)` make PostgreSQL refuse a cross-group link even if a check were missing (`apps/api/drizzle/0026_groups.sql:66`, `:68`). A route test calls every route with another group's member id and with an unknown id and expects the same 404 and no change (`apps/api/test/groups/group-routes.test.ts:481-515`).
- Enumeration: a non-member and an unknown group id raise the same `ResourceNotFound` (`group-access.ts:15`) and the test compares the bodies of all routes (`group-routes.test.ts:362-419`). A member who is not an admin gets 403, which only reveals what the caller already knows (the group exists and they belong to it).
- Invitation flow: `acceptInvitation` selects the hash and the expiry in one statement, so an unknown token, an expired token and a replaced token all throw the same `TokenInvalid` (400) (`drizzle-group-repository.ts:229-239`); the membership and capacity checks run only after the token matched, so they cannot be used to probe groups (`:241-243`); the group row is locked before the count so concurrent joins cannot pass 50 members, and the unique index on `(group_id, user_id)` is the backstop mapped to 409 (`:78-85`, `:105-108`, `apps/api/drizzle/0026_groups.sql:76`). A new invitation replaces the member's previous one (`:211-224`, unique `created_by_member_id`), which revokes a leaked link (threat R-02).
- Claim flow: the link is consumed by a single `update … where used_at is null returning` (`drizzle-group-repository.ts:279-283`), so a concurrent claim waits on the row and finds it used; unknown and already-used tokens are the same `TokenInvalid`; the ghost rebind is conditioned on `user_id is null` and the same group (`:287-297`) and only sets the user id, keeping the role `member` (a check forbids a ghost admin, `0026_groups.sql:51`); an `GroupAlreadyMember` failure rolls the used mark back, so the link stays usable (`:285-286`). `CreateClaimLink` answers 404 for a registered member or an unknown id (`create-claim-link.ts:27-28`).
- Token handling: the raw token exists only in the creation response (`group-presenter.ts:46-53`); the database holds the SHA-256 only, with unique indexes (`0026_groups.sql:25`, `:35`); lookups are by hash equality in the database, so no raw token comparison happens in application code; the response schema strips any undeclared field, so a hash cannot leak (`apps/api/src/shared/http/validate.ts:86-90`).
- Erasure: `eraseUserGroups` turns every membership of the user into a ghost named "Former member" with the role `member`, in one statement, inside the erasure transaction and before the `users` row is deleted (`apps/api/src/groups/infrastructure/db/erase-user-groups.ts:20-25`, ordered in `apps/api/src/server.ts:55-60`); this satisfies the restricting key `group_members_user_id_users_id_fk` (`0026_groups.sql:70`) and the check constraints for one row state, and nothing of the user's identity stays in the group (the display name comes from the user row through a left join, `drizzle-group-repository.ts:45`, and is stored null). A step test covers it (`apps/api/test/groups/erasure-step.test.ts`).
- Privilege escalation: `role` is no input of any route; `POST /groups/:id/members/:memberId/admin` is the only way to set it, behind `GroupAccess.admin` and `canBeAdmin` (`make-admin.ts:20-24`); the group creator is the only member inserted with `role: 'admin'` directly (`drizzle-group-repository.ts:128`).
- Migration 0026: additive (five new tables), rollback documented with a backup and run order (`apps/api/drizzle/rollback/0026_groups.down.sql:1-5`); its journal `when` must still exceed `main`'s maximum at merge (project rule).

## Threat model checklist (R-01 to R-08)

- R-01 cross-group read or change by guessing ids: mitigated by `GroupAccess` first in every use case (`group-access.ts:13-17`) and group-scoped queries (`drizzle-group-repository.ts:98`, `:147`, `:170`, `:364`); tested at `apps/api/test/groups/group-routes.test.ts:362-419` and `:481-515`.
- R-02 leaked invitation link: 256-bit token stored as a hash (`random-token-source.ts:9`, `:14`), 7-day expiry checked in the lookup (`drizzle-group-repository.ts:235`, `apps/api/src/groups/domain/group.ts:7`), a new invitation replaces the old (`:220-223`), the 50-member limit under a lock bounds the damage (`:79-85`).
- R-03 double or reused claim: atomic single-use update (`drizzle-group-repository.ts:279-283`) plus the partial unique index on unused links (`0026_groups.sql:74`).
- R-04 flooding with invitations or ghosts: one invitation row per member (`0026_groups.sql:36`), ghosts counted with members under the group lock (`drizzle-group-repository.ts:200-201`, limit `group.ts:4`). Residual group and category creation volume is Info I-2.
- R-05 self-promotion: `role` is not an input (strict bodies, `packages/shared/src/groups/group.ts:28-51`), the admin route is guarded (`make-admin.ts:20`), the check constraint forbids a ghost admin (`0026_groups.sql:51`).
- R-06 tokens in logs or URLs: tokens only in POST bodies (`group-routes.ts:127-149`), the single logger call carries ids (`group-routes.ts:100`), and the log test passes (`group-routes.test.ts:534-595`).
- R-07 erasure: `eraseUserGroups` ordered before the user delete (`server.ts:55-60`, `erase-user-groups.ts:20-25`); the rule for a group left without an admin is parent pending decision 2 (Info I-3).
- R-08 display names visible to members: `presentMember` returns the id, the display name, the ghost flag, the role and the join date only, never an email or a user id (`group-presenter.ts:21-29`); the test asserts no `@` and no user id in the detail response (`group-routes.test.ts:476-478`).
