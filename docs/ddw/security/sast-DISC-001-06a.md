## Cross-cutting checks

- Ownership and IDOR (404, never 403): every goal read or write carries the owner in the same statement through `scopedGoal(scope, id)` (`drizzle-goal-repository.ts:44`, used at `:99`, `:117`, `:153`, `:188`), so a foreign goal and a missing goal are both "no row" and become `ResourceNotFound` (404) through `notFoundUnlessAllowed` (`get-goal.ts`, `update-goal.ts:20`, `record-goal-entry.ts:25-29`, `list-goal-entries.ts:23`) or the explicit check in `delete-goal.ts:9`. Entries are reached only through the goal: `listEntries` checks the goal in scope first and returns `null` otherwise (`:187-194`), and `recordEntry` locks the scoped goal row before inserting. There is no route that takes an entry id. No route returns 403; the access policy is `OwnerOrGroupMemberAccessPolicy` with `DenyAllGroupMembershipReader`, so goals are owner-only (`goal-routes.ts:73`).
- Linked account (the link is set only at creation): `CreateGoal` resolves the account with `findLinkable`, which filters by id and `scopedTo(scope, { owner })` in one statement (`apps/api/src/goals/infrastructure/db/drizzle-account-balances.ts:22-29`), so a foreign account is a 404 and creates nothing (`create-goal.ts:28-30`); the composite key `goals_account_owner_fk (linked_account_id, owner_id) -> accounts(id, owner_id)` makes PostgreSQL refuse a foreign account even if the check were missing, and the repository maps that violation to 404 (`drizzle-goal-repository.ts:22`, `:73-76`). Balances are read with the same ownership filter in the statement that reads the opening balances (`drizzle-account-balances.ts:38-43`). Entry sums (`progressOf`) filter by `inScope` too (`:138`).
- Mass assignment: `owner_id`, `linked_account_id`, `currency`, `id` and timestamps are not in the PATCH schema (strict, three optional fields) and the repository `update` builds its `set` from `name`, `targetAmount` and `targetDate` only (`:100-104`); the owner is always `scope.userId` on insert (`:59`, `:165`), never from the body. A strict body refuses the extra key with 400 instead of ignoring it.
- Money floats: the search for `parseFloat`, `toFixed`, `Number(`, `float`, `real`, `double` and `numeric` over `apps/api/src/goals` and `packages/shared/src/goals` has no code hit (two comment hits). Amounts are `bigint` columns (`target_amount`, `amount`) and `bigint` in TypeScript; the sum is read as text (`::text`, `drizzle-goal-repository.ts:47`) and parsed with `BigInt(...)`; the request amounts are decimal strings converted with `BigInt(body.amount)` after the schema checked the format; the only number conversion is the percentage, an integer that is not money, clamped to `MAX_SAFE_INTEGER` and parsed with `Number.parseInt` over the decimal text (`goal-presenter.ts:19-22`). A test pins this (`apps/api/test/goals/no-float-money.test.ts`).
- Concurrency and limits (DoS): the 100-goal cap is counted under `pg_advisory_xact_lock` per owner, so two concurrent creates cannot both pass 99 (`drizzle-goal-repository.ts:55-63`, `MAX_GOALS = 100` at `apps/api/src/goals/domain/goal.ts:27`); entries lock the goal row with `for update` before reading the sum, so withdrawals cannot drive progress below zero and contributions cannot pass the amount ceiling (`:149-165`). The entries list is limited to 100 (schema max plus use case clamp, default 50). The account movement sums are requested in chunks of 500 ids (`drizzle-account-balances.ts:9`, `:46-47`), so one list of 100 goals cannot produce an unbounded `in (...)` list. Goal lists read progress once for the whole list instead of once per goal (`goal-view.ts` `viewsOf`). Body size is capped by the existing 16 kB parser.
- Migration 0033: additive (two new tables, indexes and keys); the composite key `goal_entries_goal_owner_fk (goal_id, owner_id)` keeps an entry's owner equal to its goal's owner; the account key restricts deletion (`ON DELETE restrict`), which the accounts module turns into `ACCOUNT_LINKED_TO_GOAL` (409), while archiving stays allowed. Rollback (`0033_savings_goals.down.sql`) drops only `goal_entries` and `goals`, states that it destroys goal data only, requires a backup and the order relative to 0032, and removes the journal row by `when`; it is fixed text. Its journal `when` must still exceed the maximum on `main` at merge (project rule).
- Erasure: `eraseUserGoals` deletes the user's goals in the erasure transaction (entries go by cascade) before the accounts, because the account key restricts (`apps/api/src/goals/infrastructure/db/erase-user-goals.ts`); it is registered in `beforeUserErased` ahead of the movements and cards steps (`apps/api/src/server.ts:59`); a step test covers it (`apps/api/test/goals/erasure-step.test.ts`).
- Secrets and PII in responses: responses carry ids, name, amounts as strings, currency, dates and derived fields; no email, user id or owner id is returned (`goal-presenter.ts`, response schemas strip anything else).
- Lint: `pnpm exec eslint apps/api/src/goals apps/api/test/goals packages/shared/src/goals packages/shared/test/goal-schemas.test.ts` reports 1 error, 0 warnings: `packages/shared/src/goals/goal.ts:42:63` `@typescript-eslint/no-unnecessary-condition` ("the types have no overlap") on `value !== undefined` inside the PATCH `refine`. It is a code-quality rule, not a security finding (the check is redundant for typing but correct at run time, and tests cover the empty-body 400); it is listed as I-3 and was fixed afterwards (eslint now reports 0 errors). `apps/api/src/goals` and `apps/api/test/goals` are clean.

## Threat model checklist (DISC-001-06a)

- Cross-owner read or change by guessing a goal id: mitigated by `scopedGoal` in every statement, same 404 for foreign and missing (`drizzle-goal-repository.ts:44`); tested in `apps/api/test/goals/goal-routes.test.ts`.
- Linking a goal to another user's account: mitigated by the scoped `findLinkable` (`drizzle-account-balances.ts:22-29`) and the composite foreign key (`0033_savings_goals.sql:31`).
- Concurrent creates or entries breaking an invariant: mitigated by the advisory lock and the row lock (`drizzle-goal-repository.ts:57`, `:157`).
- Amounts in logs: mitigated, the audit line is ids only (`goal-routes.ts:82-88`).
- Erasure leaving goals behind or blocked: mitigated by the ordered step (`server.ts:59`) and the cascade from `users`.
