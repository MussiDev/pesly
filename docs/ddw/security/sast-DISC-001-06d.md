## Findings by rule

- ✅ F-SAST-01 Hardcoded secrets (CWE-798): the secret-pattern search over the added lines finds nothing; the feature reads no environment variable and holds no credential.
- ✅ F-SAST-02 SQL injection (CWE-89): `drizzle-budget-alert-store.ts` uses only Drizzle builders (`select`, `insert ... values`, `onConflictDoNothing` (marks only), `returning`); every value (owner id, budget id, month, threshold, notice text) is a bound parameter. The budget name reaches SQL only inside the rendered notice text, as a bound value. The `categoryId` filter in `compute-spending.ts` is an in-memory comparison against the covered categories. No `sql.raw` is added. The migration and its rollback are fixed text.
- ✅ F-SAST-03 OS command injection (CWE-78): no `child_process`, `exec` or `spawn` in the scope.
- ✅ F-SAST-04 Insecure deserialization (CWE-502): the ticket adds no route and no input. The saved expense arrives through the existing validated movement routes (`POST /movements`, `PUT /movements/:id`), and the event the hook carries is built server-side from the stored movement (category id, date).
- ✅ F-SAST-05 Path traversal (CWE-22): no file access in the scope.
- ✅ F-SAST-06 XSS (CWE-79): the scope renders nothing. The notice text holds the budget name (validated by 06b on write, cut to 80 characters) as plain text; the existing notices list renders `notice.text` as a text node and a web test pins that a `budget_alert` notice renders as plain text. No `dangerouslySetInnerHTML`, `innerHTML` or `document.write`.
- ✅ F-SAST-07 SSRF (CWE-918): no outbound request; the evaluation reads the stored movement rates through the 06c readers and never calls dolarapi.com or CoinGecko.
- ✅ F-SAST-08 Broken cryptography (CWE-327): no cryptography in the scope; the only generated value is `gen_random_uuid()` for the mark id, which is not a secret.
- ✅ F-SAST-09 Debug mode in production (CWE-489): no debug flag, no `console` call, no `NODE_ENV` branch.
- ✅ F-SAST-10 Logging sensitive data (CWE-532): the only added log call is `logger.error(failure, 'budget alert evaluation failed')` in `server.ts` and `worker.ts`, where `failure` is `{ errorName, errorCode, userId }` built by `describeFailure` in `best-effort-expense-saved.ts`. The error object and its message are never logged, because a driver error carries the statement and its parameters (the notice text, so the budget name). No amount, category, threshold or budget name reaches a log. Tests assert it (`alerts-flow.test.ts` "still answers 201 when the store fails and logs the error name and code, no budget name or amount (AC-18)", `expense-saved-hook.test.ts` "reports the error name and the AppError code, never the message").
- ✅ F-SAST-11 Unrestricted upload (CWE-434): no upload surface.
- ✅ F-SAST-12 Missing CSRF protection (CWE-352): no new route and no new state-changing entry point; the evaluation is a side effect of the existing session-protected movement writes.
- ✅ F-SAST-13 Critical/High CVE in a dependency: no dependency added or changed (no `package.json` or lockfile in the diff), so the last `pnpm audit --prod --audit-level high` on main is unchanged; the audit was not re-run for this report.
- ✅ F-SAST-14 Incomplete input validation (CWE-20): the evaluator trusts no request value. The month comes from the `Clock`, the stored time zone and the stored movement date; the category id comes from the stored movement; the threshold list comes from 06b, which validates 1 to 200. Defence in depth in the database: `budget_alert_marks_threshold_check` (1 to 200) and `budget_alert_marks_month_check` (first day of month), and `renderNoticeText` throws on a threshold that is not an integer from 1 to 200.
- ✅ F-SAST-15 Insecure error handling (CWE-209): the hook never throws and never changes the response of the movement write; an evaluation error or a timeout becomes one log line with ids only. No error detail reaches the client. Errors are not swallowed anywhere else: the evaluator and the store rethrow, and the one handler is `BestEffortExpenseSavedHook` (tested for rejection, late rejection and time bound).
- ✅ F-SAST-16 Medium CVE in a dependency: none, no dependency changed.

## Cross-cutting checks

- Ownership and IDOR: the owner id is `scope.userId` of the saved movement, never an input. The version reader and the spending reader scope every read by that id (06b and 06c code, unchanged), so another user's budget over the same category is never read (`alerts-use-case.test.ts` "reads only the budgets that cover the category and never another owner", `alerts-flow.test.ts` "notifies the owner only, never a user with a budget over an identically named category"). `DrizzleBudgetAlertStore` writes marks and notices with `scope.userId` and reads the language from `users` by that id. The composite foreign key `(budget_id, owner_id)` to `budgets (id, owner_id)` makes the database refuse a mark whose budget belongs to another owner (`alerts-store.test.ts` "rejects a crossing of a budget of another user and writes nothing", `alert-marks-migration.test.ts`). The hook is built by the movements module with a write scope only after the route's session and ownership checks, and a request with no session or another user's movement never reaches it.
- Race and duplicates: one `db.transaction` inserts the marks with `ON CONFLICT DO NOTHING` on the unique key `(budget_id, month, threshold)` and inserts a notice only for a row the insert returned, so two concurrent saves publish one notice (`alerts-store.test.ts` "creates exactly one mark and one notice for two concurrent calls", `alerts-flow.test.ts` "leaves exactly one notice for two simultaneous requests"). If the notice insert fails the mark rolls back with it (`alerts-store.test.ts` "rolls the mark back when the notice cannot be written"), so a threshold is never marked without its notice. A budget deleted between the read and the write violates the composite foreign key, the transaction rolls back and the hook logs the failure; nothing is half written.
- Money: the search for `parseFloat`, `toFixed`, `Number(` and float, real, double or numeric column types over the added source and the migration returns no hit. The percentage is the 06c `bigint` division rounded down, and `crossedThresholds` compares integers. The notice text takes no amount. `no-float-alerts.test.ts` scans the feature and the 0036 migration on every run.
- Data exposure in text: `renderNoticeText` receives only the budget name and the threshold for this kind, so no amount, currency figure, account name or category name can reach the stored text (`notice-text.test.ts`, `no-sensitive-text.test.ts`).
- DoS bounds: the evaluation filters to the budgets that cover the saved category and issues the same two aggregated statements as 06c (not one per budget); the wrapper bounds the wait at 2,000 ms. A benchmark covers the added p95 for 50 budgets and 100,000 movements against the 100 ms limit (`perf/budget-alerts.perf.test.ts`; figures are in the PR description, not measured for this report). See I-1 for what the bound does not stop.
- Statelessness: no process-level state, cache or queue; marks and notices live in PostgreSQL (`alerts-flow.test.ts` "publishes the same notices from a second API instance"). The timer in the wrapper is local to one call and is cleared in `finally`.
- Migration 0036: additive, one `CREATE TABLE` with its constraints and the widening of `notices_kind_check` (drop and re-add with the fifth kind); no data change. The rollback `0036_budget_alert_marks.down.sql` is idempotent, states the run order (before the rollback of 0035) and the backup step, deletes the `budget_alert` notices because the restored check would refuse them, restores the four-kind check guarded by `to_regclass`, drops the table with `IF EXISTS` and removes the journal row by `created_at = 1791800000000`; the marks are lost by design, so thresholds alert again after a re-apply, and the header says so. The journal `when` (1791800000000) exceeds the previous entry (1791790000000) and must exceed main's maximum at merge (project rule); `alert-marks-migration.test.ts` pins the chain.
- Erasure and cascade: `budget_alert_marks` cascades with the budget and, through `budgets`, with the user; the notices of the owner cascade with the user (`notices.owner_id` references `users` with `ON DELETE CASCADE`), so account erasure needs no new step.
