## Cross-cutting checks

- Authorization on every route: all six new routes run behind `requireSession` and `requireVerifiedEmail` (`group-routes.ts:175`) and take the caller's id from the session (`userIdOf(auth)`), never from input. Every use case resolves the caller's membership first through `GroupAccess` (`get-balances.ts:21`, `record-settlement.ts:71`, `preview-consolidation.ts:36`, `list-settlements.ts:27`, `leave-group.ts:22`); removal uses `GroupAccess.admin` (`remove-member.ts:24`), so a member who is not an admin gets 403 and a non-member 404. A user who left is outside every lookup: the `active` filter (`left_at is null`) is on `findMember`, `findMemberById`, `getSummary`, `listForUser` and the membership reader (`drizzle-group-repository.ts:76`, `drizzle-group-membership-reader.ts:13`), so access scopes of other modules also stop at the exit. No self-removal: the admin route refuses the caller's own member id (`remove-member.ts:25`, `CannotRemoveSelf`, 400) and leaving is a separate route that can only act on the caller's own member row (`leave-group.ts:23-27`).
- IDOR through account, member and settlement ids: member ids from the body, the query or the path are checked against the active members of the already-authorized group (`record-settlement.ts:78`, `:118-124`, `:143`; `preview-consolidation.ts:343`; `remove-member.ts:26`) and again under lock (`group-locks.ts:26-45`); the composite foreign keys `(from_member_id, group_id)`, `(to_member_id, group_id)`, `(created_by_member_id, group_id)` and `(account_member_id, group_id)` make PostgreSQL refuse a cross-group member even if a check were missing (`0028_group_settlements.sql:34-37`). The account is read through the caller's owner scope only, with group read access denied (`drizzle-settlement-account-checker.ts:12-26`), so another user's account is not found and answers `GROUP_SETTLEMENT_ACCOUNT_INVALID`; the account is accepted only when the caller is a party and it is stored with the caller's own member id (`record-settlement.ts:86-97`), and a check forces that member to be one of the two parties (`0028_group_settlements.sql:23`). Every list, leg and aggregate query carries the group id of the authorized group (`drizzle-group-settlement-repository.ts:121-127`, `:164`, `:174`, `:184`, `:194`, `:300`); the account sums adapter returns sums only for the ids it was given (`drizzle-account-movements.ts:43-50`).
- Lock ordering and deadlocks: every write path takes the group row first and member rows after, and member rows always in id order. Settlement: group `for update`, then members `for share` ordered by id (`drizzle-group-settlement-repository.ts:228-231`, `group-locks.ts:37-44`); expense: group `for share`, then members `for share` (`drizzle-group-expense-repository.ts:135-142`); removal: group `for update`, then the one member row `for update` (`drizzle-group-repository.ts:410-418`); join and ghost creation already take the group `for update` (`:231`, `:272`). No path takes a member row and then waits on the group row, so there is no cycle; the lock-wait cases are tested (`drizzle-group-settlement-repository.test.ts:368`, `drizzle-member-removal.test.ts:444`).
- Atomicity: the settlement, its legs and the log row are written in one `db.transaction` (`drizzle-group-settlement-repository.ts:226-282`); a removal sets `left_at`, deletes the removed member's invitations and unused claim links and resets a percentage split in one transaction (`drizzle-group-repository.ts:406-436`); tests prove that a failure after the leg insert and a failure inside the removal leave nothing behind (`drizzle-group-settlement-repository.test.ts:152`, `drizzle-member-removal.test.ts:286`).
- Money integrity: amounts, legs and rates are `bigint` end to end (`0028_group_settlements.sql:4`, `:15`, `:21`); balances are derived on read from three `sum(bigint)::text` aggregates read with `BigInt` (`drizzle-group-settlement-repository.ts:143-148`, `member-balances.ts:41`), so values past 2^53 stay exact (`drizzle-member-removal.test.ts:172`); `convertMinorUnits` and `simplifyDebts` use only `bigint` arithmetic, round half up on the magnitude and assert that the balances add up and that the payments clear every balance (`convert-minor-units.ts:19-24`, `simplify-debts.ts:37`, `:72-74`); the sum of balances is checked after 10,000 mixed operations against an independent ledger (`apps/api/test/groups/balances-random-operations.test.ts:42`); no `parseFloat`, `toFixed`, `Math.` or float column in the source scope (grep). Overflow of the 64-bit column by a consolidation at an extreme manual rate is finding W-SAST-01 L-1.
- Cursor tampering and DoS bounds: the cursor is unsigned but decoded strictly (`keyset-cursor.ts:24-40`) and only positions a query already scoped by group (`drizzle-group-settlement-repository.ts:300`); `limit` max 100, cursor at most 512 characters, body at most 16 kB (`apps/api/src/app.ts:20`), at most 50 active members (`apps/api/src/groups/domain/group.ts:5`) so the consolidation and the debt plan work on at most 50 parties; legs are loaded only for the page's ids (`drizzle-group-settlement-repository.ts:108-135`); the balance read is four aggregates over indexed columns, measured at p95 below 500 ms for 50 members and 10,000 expenses (`apps/api/test/perf/group-balances.perf.test.ts:44`).
- Mass assignment: every body and query is a `z.strictObject`, `createdByMemberId` and `accountMemberId` are derived from the session (`record-settlement.ts:96`, `:107`), the rate source and type are set by the use case (`:174`, `:178`), never read from the request, and the removal and leave routes read no body.

- Migration 0028: additive for data (two new tables, one nullable column), with the member unique index narrowed to active members and the activity log check widened (`0028_group_settlements.sql:36`, `:44-47`); the rollback is documented with a backup, run order and a guard that refuses to run while a member has `left_at` set (`apps/api/drizzle/rollback/0028_group_settlements.down.sql:1-20`); its journal `when` is above 0027's and must still exceed `main`'s maximum at merge (project rule).

## Threat model checklist (R-01 to R-09)

- R-01 a non-member or a user who left reads balances or records settlements by guessing ids: mitigated by `GroupAccess` first in every use case, the `left_at is null` filter on every membership lookup and group-scoped queries (`record-settlement.ts:71`, `get-balances.ts:21`, `drizzle-group-repository.ts:76`), same 404 for missing, foreign and left groups; tested at `group-settlement-routes.test.ts:744`, `:759`, `settlement-use-cases.test.ts:811`, `:829`, `:835` and `drizzle-group-settlement-repository.test.ts:470`.
- R-02 a member attaches another user's account to a settlement: the account must be the caller's own, open and in the cash currency, and the caller must be a party (`record-settlement.ts:86-97`, `drizzle-settlement-account-checker.ts:22-26`), with the check constraint on `account_member_id` as backstop (`0028_group_settlements.sql:23`); tested at `settlement-use-cases.test.ts:416`, `group-settlement-routes.test.ts:372` and `settlement-account-balance.test.ts:186`.
- R-03 balances stop adding up: derived on read from the three sources, zero-sum per operation, integer helpers with asserted sums (`simplify-debts.ts:37`, `:72-74`); tested with 10,000 operations (`balances-random-operations.test.ts:42`, `settlement-use-cases.test.ts:982`) and 20 concurrent settlements (`drizzle-group-settlement-repository.test.ts:272`).
- R-04 a member leaves with a balance because of a concurrent expense: group lock then member row lock on removal, the balance read inside that transaction, and the `for share` recheck on every write path (`drizzle-group-repository.ts:410-422`, `drizzle-group-settlement-repository.ts:231`, `drizzle-group-expense-repository.ts:135-142`); tested at `drizzle-member-removal.test.ts:444` and `drizzle-group-settlement-repository.test.ts:237`, `:418`.
- R-05 a consolidated settlement clears debts the user did not see: the legs sent are compared with the stored ones in the use case and again under the group lock inside the write transaction, 409 on any difference (`record-settlement.ts:146-151`, `drizzle-group-settlement-repository.ts:234-243`); tested at `settlement-use-cases.test.ts:614`, `group-settlement-routes.test.ts:461` and `drizzle-group-settlement-repository.test.ts:344`.
- R-06 the last admin leaves and the group cannot be managed: `GROUP_LAST_ADMIN` while other members remain, evaluated under the group lock so two admins cannot leave each other (`drizzle-group-repository.ts:423`, `:440-449`); tested at `drizzle-member-removal.test.ts:199`, `settlement-use-cases.test.ts:951` and `group-settlement-routes.test.ts:718`.
- R-07 account erasure fails because settlements reference accounts: `on delete set null` on `account_id` and surviving ghost member rows (`0028_group_settlements.sql:42`), tested at `settlements-migration.test.ts:248` and `former-member-erasure.test.ts:62`.
- R-08 the balance query is slow in large groups: aggregates grouped by currency and member over the indexes `(group_id, currency)` and `(group_id, occurred_at, id)` (`0028_group_settlements.sql:46-48`), benchmark at `apps/api/test/perf/group-balances.perf.test.ts:44`.
- R-09 sensitive text in logs: audit lines carry ids only (`group-routes.ts:162-170`, `:455`, `:504`, `:514`), the 409 balance travels in the response body only, and the error logger never logs `details` (`error-handler.ts:133-138`); tested at `settlement-audit.test.ts:33`, `:73`, `:101`.
