## Findings by rule

- ✅ F-SAST-01 Hardcoded secrets (CWE-798): the secret-pattern search over the added lines finds nothing; the module reads no environment variable and holds no credential.
- ✅ F-SAST-02 SQL injection (CWE-89): every value reaches PostgreSQL as a bound parameter. In `apps/api/src/budgets/infrastructure/db/drizzle-spending-reader.ts` the window instants are bound ISO text cast to `timestamptz` (`:23`), the category ids go through `inArray` (`:67`), the owner through `scopedTo`, and the sums are `sum(...)::text` over columns. The only `sql.raw` calls are the constant group-by ordinals `'1, 2, 3, 4'` (`:80`) and `'1, 2, 3, 4, 5'` (`:133`), literals with no interpolation, needed because the bucket expression carries bound parameters. `drizzle-budget-version-reader.ts` is pure Drizzle builders (`inArray`, `eq`, `lte`, `scopedTo`) with the month converted to a first-of-month date by `monthStartOf`, which parses a validated `YYYY-MM`. The migration and its rollback are fixed text.
- ✅ F-SAST-03 OS command injection (CWE-78): no `child_process`, `exec` or `spawn` in the scope.
- ✅ F-SAST-04 Insecure deserialization (CWE-502): both new routes go through the one `validate` middleware with shared Zod schemas (`budget-routes.ts`, `/budgets/spending` with `budgetSpendingQuerySchema`; `/budgets/:id/spending` with `budgetIdParamsSchema` and the query schema); the query is a `z.strictObject`, so an unknown key is refused; the month is a regex-checked `YYYY-MM` string (`packages/shared/src/budgets/spending.ts:8-10`); no route reads `req.query` or `req.params` directly; responses are parsed with `budgetSpendingResponseSchema` and `budgetSpendingListResponseSchema`.
- ✅ F-SAST-05 Path traversal (CWE-22): no file access in the scope; the budget id is UUID-validated.
- ✅ F-SAST-06 XSS (CWE-79): the scope renders nothing; the web change adds one error key and its mapping; no `dangerouslySetInnerHTML`, `innerHTML` or `document.write`. The budget name returned in the response was validated by 06b on write.

## Cross-cutting checks

- Ownership and IDOR: the owner id comes from the session scope, never from input. The personal query carries `scopedTo(scope, { owner: movements.ownerId })` and joins `accounts` on both id and owner (`drizzle-spending-reader.ts:59-61`, `:65`). The version reader scopes `budgets`, `budget_versions` and `categories` by owner (`drizzle-budget-version-reader.ts:35`, `:59`, `:125`), so a foreign budget id yields no row and the use case answers 404, never 403 (`spending-routes.test.ts` "answers 404 for a foreign and an unknown budget with the same body"). The version-category and threshold reads use version ids that were already selected through the owner scope.
- Group data exposure: `shareSpending` reaches `group_expenses`, `group_expense_shares` and `group_categories` only through `group_members` rows with `user_id = scope.userId` (`:127`, the same rule as `GET /groups/personal/shares`), asserts an issued scope (`assertIssuedScope`) and returns only the caller's own share amount and the group category name. Another member's share, name or payer is never selected. The left join to `movements` is restricted to `movements.owner_id = scope.userId`, so it can only carry the caller's own payer movement rate (tested in `spending-reader.test.ts` "carries the payer movement rate only when the caller paid" and "ignores shares of 0, groups the caller is not in, and expenses outside the window").
- Money: the search for `parseFloat`, `toFixed`, `Number(` and float, real, double or numeric column types over the added source returns no hit; sums are read as text and parsed with `BigInt`, rates are integers scaled by 10,000, conversion is integer arithmetic (`domain/spending.ts`), and `no-float-spending.test.ts` scans the feature and the 0035 migration on every run. Amounts leave as exact integer strings.
- DoS bounds: at most 50 budgets per user (06b), so a list asks for at most 50 versions and a bounded category set; the readers issue a fixed number of statements (one per month asked for the versions, one for personal spending, one for shares), never one per budget, and a benchmark measured p95 of 137.6 ms and 99.8 ms for 50 budgets and 100,000 movements against a limit of 500 ms. The window is at most two months, and the month cannot be in the future or before 1971.
- Audit logging: see F-SAST-10; the list call logs the user id and request id only.
- Migration 0035: additive, one `CREATE INDEX ... WHERE payer_movement_id IS NOT NULL` on `group_expenses`, no data change, no lock beyond the index build on a table that is small compared with movements. Rollback `0035_group_expense_payer_movement_idx.down.sql` drops the index with `IF EXISTS`, is idempotent, states the run order, and removes the journal row by `created_at = 1791790000000` guarded by `to_regclass`; it loses nothing, since the index holds no data of its own. The journal `when` (1791790000000) exceeds the previous entry (1791780000000) and must exceed main's maximum at merge (project rule); `spending-migration.test.ts` pins the chain.
- Erasure and cascade: the ticket stores no new data, so account erasure needs no new step.
