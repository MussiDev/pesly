- ✅ F-SAST-02 SQL injection (CWE-89): not applicable, the scope has no database access; every call goes to the API.
- ✅ F-SAST-03 OS command injection (CWE-78): browser code only, no `child_process`, `exec` or `spawn`.
- ✅ F-SAST-04 Insecure deserialization (CWE-502): every new call parses its answer with a shared Zod schema and turns a mismatch into the generic `INTERNAL` failure, never partial data (`api-client.ts:714-715`, schemas at `:1578`, `:1586`, `:1596`); the error body goes through `errorResponseSchema` and the balances are read only when both are integer strings (`readBalances`, `api-client.ts:367-373`); the screens add no `JSON.parse`, no `localStorage` and no `sessionStorage`.

## Cross-cutting checks

- Invitation and claim token, address bar and history: the link carries the token in the fragment only (`group-link.ts:13`, `#token=` plus `encodeURIComponent`), so no server, proxy, access log or Referer header ever receives it. The link pages read it once with `takeFragmentToken` and remove it with `history.replaceState(null, '', pathname + search)` (`take-fragment-token.ts:9`), which rewrites the current entry and adds none (`pushState` is never used in the scope); `pathname` and `search` come from the current location, so the replacement URL holds no token and no query of the token. The hook calls it before `send` (`use-group-link.ts:48-54`), so the clearing happens before the join or claim request. No query string is ever built: the request is `POST /groups/join` or `/groups/claim` with the token in the JSON body (`api-client.ts:1610-1629`). A test asserts that no `replaceState` URL contains the token (`apps/web/test/group-link-pages.test.tsx:61-70`).
- One request per attempt, strict mode and retry: a `useRef` guard makes React's development double mount skip the second run (`use-group-link.ts:29,46-47`; refs survive the strict-mode remount), so the token is read and sent once. The retry exists only for the `network` failure (`link-result.tsx:37-46`) and re-sends the token kept in the ref (`use-group-link.ts:58-61`), in memory only, never in storage, the URL, a state value or the DOM; a reload drops it and shows the invalid-link state. See I-1 for the transport-level repeats of the session refresh.
- Link pages in the authenticated shell: the children of the shell mount only after the session is confirmed (`authenticated-shell.tsx:82-111`), so the token is not read while the guard still decides, and an unauthenticated visitor is sent to sign-in by the guard (`authenticated-shell-container.tsx:83`) before any join request; the fragment sits in the address bar until then (I-2).
- Clipboard and share: the link is shown only to the member who asked for it, in a read-only field that stays visible (`share-link.tsx:39-46`); `navigator.clipboard.writeText` and `navigator.share` run only on a click, inside `try/catch` blocks that report a failed copy and ignore a closed share sheet (`:19-35`); the share call passes `url` and a catalog title and no other field; the link is not logged, stored or sent to another origin by the app; what the user does with a copied link is accepted (threat model R-06: single group, member limited, 7 days).
- Open redirects and id shapes: every `router.push` and `router.replace` in the scope targets a static path (`/sign-in`, `/groups`) or `/groups/` followed by the id of a parsed API answer (`use-group-link.ts:37`, `create-group-container.tsx:43`); the path is always relative and prefixed, so it cannot leave the origin or become a `javascript:` URL; the id of an answer is checked only as a string (L-1). The route param `groupId` goes only into a path segment through `resourcePath` and into relative `Link` hrefs.
- Admin controls hidden, API authoritative: the rate-type control and the category management render only for `role === 'admin'` (`group-detail-container.tsx:188`, `group-categories-container.tsx:205,209,229`), the promote and remove controls take `canAdmin` from the same role, and the role is the one the API returned for this caller; every action sends only ids taken from the loaded group and the API answers 403 or 404, shown as a catalog message (`GROUP_ADMIN_REQUIRED`, `api-client.ts:300`); invitations, members without an account and claim links are open to every member by the API rules (no admin check in `create-invitation`, `add-ghost-member`, `create-claim-link`) and the screens show them to every member, consistent with it. No permission is derived on the client.
- Information disclosure for 404: the detail and categories screens render one not-found state for a missing group, a group of someone else and a user who left, with no name, count or hint; the list shows only what `GET /groups` returns for the caller; the link pages answer one generic invalid-link message for every token failure.
- Sensitive data in the DOM: the invitation or claim link is in the page only for the member who created it, inside the read-only input (`share-link.tsx:41`), and goes away when the panel unmounts; no token, email, user id or account number is rendered; balances appear only in the leave and removal refusal for the caller's own group; member rows show the display name and a ghost badge only.
- Money formatting: the only amounts on these screens are the balances of a refused leave or removal; they are integer strings kept as `BigInt`, negated and compared as `BigInt` (`group-issue.tsx:31-35`) and formatted by `formatMoney`; the scope has no `Number`, `parseFloat`, `toFixed` or `Math` call on money (searched).
- Error messages echoing server text: none; `messageKey` comes from the fixed table at `api-client.ts:256`, and `tAll(failurePath(failure))` can only produce an `errors.*` path of that type (`group-failure.ts:11`).
- Supply chain: no manifest or lockfile change, no new import source, no remote script, font or image in the scope.

## Threat model checklist (R-01 to R-06)

- R-01 a token leaks through server logs, the Referer header or browser history: mitigated by the fragment form, `replaceState` before the request and the body-only transport (`group-link.ts:13`, `take-fragment-token.ts:9`, `use-group-link.ts:48`, `api-client.ts:1614`); tested at `group-link-pages.test.tsx:61-70` and by the end-to-end invalid-link flow (`apps/web/e2e/groups.spec.ts:83-92`).
- R-02 a token is consumed twice by a double mount or a retry: mitigated by the `started` ref and a retry only for a network failure (`use-group-link.ts:29,46,58-61`, `link-result.tsx:37-46`); the residual transport-level repeats are I-1.
- R-03 a member uses admin actions by forging requests: the screens hide the controls and the API is the authority (`group-detail-container.tsx:188`, `group-categories-container.tsx:205`); a 403 is shown as the catalog message (`api-client.ts:300`, `group-issue.tsx:47`).
- R-04 a screen leaks the existence of a group to a non-member: one not-found state for every 404 (`group-detail-container.tsx:60`, `group-categories-container.tsx:61,67`) and one invalid-link message for every token failure (`use-group-link.ts:14-16`).
- R-05 a hardcoded string or one-language screen ships: every string in the scope goes through `useTranslations`; both catalogs gained the same 130 lines; the end-to-end suite adds the hardcoded-strings scan (commit `72a96c9`). Not a security control beyond the mapping of codes to keys, which is complete for the new codes.
- R-06 the link is copied to an untrusted place: accepted by design (copying is the feature); the link is single group, member limited and expires in 7 days; the clipboard and share calls are user initiated and failure tolerant (`share-link.tsx:19-35`).
