# Pesly audit — 2026-10-13

Read-only review of code, UX and features. Nothing was run end to end (no app, no tests, no e2e); findings come from reading code and PRDs. Items marked "verify" need confirmation.

## 1. Reported problems

### 1.1 Group payments do not change net worth, but change the bank balance — mostly by design
- Account balance = opening + movements + settlement cash (`apps/api/src/movements/infrastructure/accounts/drizzle-account-movements.ts:42-52`).
- Net worth = accounts + investments + group net − installment debt (`apps/api/src/dashboard/domain/net-worth-now.ts:54-91`). Collecting a settlement raises the account and lowers the receivable by the same amount, so net worth is flat. A settlement is neither income nor expense (AGENTS.md glossary).
- If the money is real external income, it must be recorded as an income movement.
- **Real gap (FEAT-008):** when another member records "Ana paid X", no movement is written to Ana's account. Her receivable counts in net worth (`dashboard/infrastructure/db/drizzle-group-balance-reader.ts:75`) but her account is not reduced, so net worth is overstated by about X until she adopts or creates the payer movement. FEAT-008 fixes this.
- Minor: consolidated settlements convert at today's rate in net worth but at the settlement rate in the account, so small drift is possible.
- Severity: medium.

### 1.2 Manual balance edit rewrites history — confirmed bug
- The UI only edits the opening balance (`apps/web/src/features/accounts/components/account-row.tsx:128-201`). `SetOpeningBalance` (`apps/api/src/accounts/application/set-opening-balance.ts:20-29`) runs `UPDATE accounts SET opening_balance`. No trace is left.
- The income-vs-expense report reads movements only (`reports/infrastructure/db/drizzle-flow-reader.ts:32-74`), so the balance moves with no income or expense to explain it.
- Net-worth history treats `opening` as constant (`net-worth-now.ts:59`), so the whole past curve is rewritten.
- **Fix:** add an `adjustment` movement type (signed, account required, no category/rate). Add a "Set current balance" action: the user types the target and the server creates an adjustment of (target − current). Exclude adjustments from `personalConditions` (reports/budgets), include them in account balance and account flows. Opening balance stays editable only at creation. Handle `adjustment` explicitly in all three readers: `drizzle-account-movements.ts`, `drizzle-account-flow-reader.ts:33` (it treats every non-income type as negative) and `flow-conditions.ts`.
- Severity: high (trust).

### 1.3 Card installments feel strange; no shared card expenses
- Arithmetic is correct (leftover on cuota 1, `packages/shared/src/money/split-installments.ts:8-24`).
- The form (`installment-form.tsx`) shows no schedule: no amount per cuota, no statement or due date per cuota. This is the main source of the "strange" feeling. One field ("1 to 60") switches between a plain card expense and an installment purchase, which have different semantics.
- Purchase on the closing day lands in the closing statement (`closingDate >= day`); many banks put it in the next one, and the form never says which. A back-dated purchase silently goes to the oldest statement, which may be closed.
- Installments live in a separate table, so reports filtered by account or tag exclude them, and USD cuotas have no rate (see the report caveats in `es.json`).
- PRD drift: 10c FR-02/AC-03 says reject USD installments; code accepts them.
- **Shared expenses with a card:** confirmed missing. The groups module has no reference to cards or installments; 10b and 10c list it as out of scope; 05i says installments cannot be sent to a group. A one-payment group expense can only be recorded as a full-amount movement on the card's account.
- **Proposed design (needs its own PRD):** the payer's card is charged the full amount; optional `cardId` + `payerInstallments` (2–60) on the group expense payer; on save create an installment purchase linked to the group expense; group balance stays on the full amount; the payer's personal monthly expense is only their share (`share / count` per cuota); edits and deletes propagate; the form previews each cuota. Open question: interaction with the "share counts as personal expense" rule.
- Severity: high (core Argentine use case).

## 2. Code quality

Largely clean on the hard rules: 0 `any`, 1 justified eslint-disable, 0 TODO/FIXME, 0 domain→infrastructure imports, all routes validated, no float money functions, no hardcoded colors except Google logo fills, no fetch in presentational components, no `"use server"`, ESLint without errors.

Ranked findings:
1. **High** — `apps/web/src/lib/api-client.ts` is 2,319 lines, every module mixed with transport and error parsing. Split per module (`lib/api/*.ts` + shared `http.ts`), re-export from the old path.
2. **Medium** — large files: `group-routes.ts` (774), `movements-container.tsx` (679), `group-queue.ts` (616), `drizzle-group-expense-repository.ts` (601), `identity/index.ts` (599), `movement-form.tsx` (530). Groups has 5 files over 470 lines.
3. **Medium** — web has few co-located tests (4 of 555 source files; tests may live elsewhere — verify). The 80% threshold is global, so API coverage can mask web. Add a per-directory threshold for `apps/web/src`.
4. **Low-medium** — 11 identical `.catch(() => undefined)` stream cancels in the API adapters (dolarapi, Google OIDC, CoinGecko), against the "no silent catch" rule. Extract `discardBody()` with a why-comment. `api-client.ts:928` and `:969` swallow errors and deserve a second look.
5. **Low** — `pnpm lint` fails Prettier on 2,107 files (line endings). Add `.gitattributes` (`* text=auto eol=lf`) and set Prettier `endOfLine`.

## 3. UI/UX (Apple direction)

Strengths: tokenized OKLCH theme with a contrast test, dark mode, skeleton/error/empty states widely used, reduced-motion respected, es/en catalogs with identical keys.

Weaknesses: generic navy fintech look; flat cards on low-contrast grey; 24 px titles with no large title; no blur or materials; no sheet primitive (filters use native `<details>` + `<select>`); `ListRow` has hover but no pressed state, no grouped container, no chevron; accounts and cards (core) hidden under "More" with about 10 destinations; manifest has no icons, `theme_color` or `background_color`, and no viewport export (breaks install prompt, status bar tint, `viewport-fit=cover`).

Direction, by impact:
1. Large-title header collapsing into a blurred sticky bar; add 34 px title and 17 px body tokens.
2. `InsetGroup` + rebuilt `ListRow`: 12 px radius, hairline inset separators, chevrons, `active:` pressed state; background `#F2F2F7` / dark `#000`.
3. Materials: `bg-background/70 backdrop-blur-xl` on top and bottom bars.
4. Bottom-sheet primitive (Radix Dialog, grabber, spring) for filters, confirmations, quick add.
5. One bright system-blue accent; navy only for the hero, or none.
6. System font stack (or Inter) with tabular numerals for amounts.
7. Motion: `active:scale-[0.97]`, spring easing, keep the reduced-motion rule.
8. Promote Accounts or Cards to a tab; group budgets/goals/recurring under a "Plan" hub.
9. Segmented control, switch, and sheet picker instead of native `<select>`.

Quick wins (under a day each): manifest icons/colors + viewport export; `backdrop-blur` on both bars; pressed states; background and radius tokens; body to 17 px; filter sheet; delete dead `coming-soon.tsx`.
